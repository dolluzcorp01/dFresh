# 04 - Languages (i18n) design

Goal: today English, Tamil, Hindi. Tomorrow Telugu, Kannada, maybe Arabic (right-to-left).
**Adding a language must be data entry, not a code change.**

## URL scheme
- Every public page has a language prefix: `/en`, `/ta`, `/hi` (+ `/en/products`, `/ta/products?cat=napkins`, `/en/privacy` ...).
- `/` redirects to the visitor's saved language (localStorage `dfresh-lang`), else the browser language if it is
  an active language, else the default (`en`).
- Unknown or inactive prefix -> redirect to the same path in the default language.
- This gives clean `hreflang` alternates and lets Google index each language separately.

## Data flow
1. On load the app calls `GET /api/dfresh/languages` (active languages, default, labels, html_lang, dir, font).
2. Then `GET /api/dfresh/bootstrap?lang=xx` returns everything the site needs in ONE cached response:
   ui text map, categories, products (+ variants, images), banners, kits, towns, form options, size picker,
   public settings. Every text already has the English fallback applied on the server.
3. `I18nProvider` stores it; `useT()` gives `t('know_more')` and `t('results', { n: 7 })` (simple `{name}` placeholders).
4. Switching language: navigate to the same path with the new prefix, fetch that language's bootstrap
   (cache in memory per language), update `<html lang dir>`, load that script's font, save to localStorage,
   send GA4 `language_change`. The selected product colour, open filter and scroll position survive the switch.

## Rendering rules
- Components receive keys or data objects, never English sentences.
- Missing key in the map -> show the English value; in development also `console.warn` once per key.
- `allows_html = 0` keys render as text (React escapes). Only keys flagged `allows_html = 1` may use a tiny
  safe subset (`<br>`, `<em>`), sanitised on the server.
- Fonts: `languages.font_family` is loaded on demand. CSS uses `var(--f-body)` / `var(--f-disp)`, which the
  provider sets per language (it sets `--f-lang` to `font_family`; Saira stays the brand display font).
  Headline sizes for long scripts are tuned through `[data-script="long"]` on `<html>`. Phase 2 derives it
  from data: a language whose `font_family` differs from the default language's gets `long` (Tamil, Hindi
  today; a new Telugu row would too). A languages column can replace this later - never a language code.
- Header width: the header switches to its compact layout (menu sheet) whenever the full nav does not fit,
  measured in the browser, so a language with longer labels never causes sideways scroll.
  Long scripts first get a smaller nav (14px, smaller gap) so desktop (>= 1280px) keeps the inline links;
  the header measures again after the script font and `data-script` are applied. Keep nav labels short
  (Tamil uses short forms, e.g. nav_where "வாங்க").
- "Page did not load" screen: it shows when the API is unreachable, so it cannot fetch its text.
  `npm run i18n:fallback` (also run by `prebuild`) snapshots those few keys (`load_err_h`, `load_err_p`,
  `retry`, `whatsapp_us`, `wa_general`) for every active language into `src/i18n/fallbackText.json`.
  Re-run it after editing those texts in the admin.
- Direction: set `<html dir>` from `languages.dir`. Use logical CSS properties (`margin-inline-start`,
  `padding-inline`, `inset-inline-end`) everywhere so RTL works without rewrites.
- Numbers, phone numbers, product IDs and sizes stay in Latin digits.
- Spec and pack text are English in the Excel today; the schema already has per-language override columns.

## Adding a language (the procedure that must work)
1. Admin -> Languages -> Add: code `te`, name `Telugu`, native `తెలుగు`, switch label, html_lang `te-IN`,
   dir `ltr`, font `Noto Sans Telugu`, **inactive**.
2. Admin -> Translations: fill missing values (grid shows a red count per language), or Export the
   translation sheet, translate, Import it back. Product text via the product Excel (adds `_TE` columns).
3. Upload a Telugu brochure (optional; English is the fallback).
4. Switch the language **active**. It appears in the switcher, routes, hreflang and sitemap automatically.
No deploy, no code change. Phase 7 must prove this with a test language.

## Translation quality
Tamil and Hindi seed text was drafted with AI. A native speaker must review before go-live
(tracked in 07_ACCEPTANCE_AND_OPEN_ITEMS.md). Do not "fix" wording silently in code; change it in the admin.
